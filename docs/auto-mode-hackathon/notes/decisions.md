# Решения

## D-001 — Scope демо

Дата: 2026-09-05

Решение: разрабатываем только CLI/backend. VS Code, JetBrains и Agent Manager не входят в scope.

Следствие: UX может быть реализован через `kilo run`, TUI slash command и существующий session API; клиентские extension-интеграции не требуются.

## D-002 — Рабочая память в репозитории

Дата: 2026-09-05

Решение: исследования, части ТЗ, implementation reports и handoff notes хранятся в `docs/auto-mode-hackathon/`.

Следствие: следующий агент сначала читает `README.md` и `research/`, затем обновляет память вместе с кодом.

## D-003 — Поддерживаемые платформы демо

Дата: 2026-09-05

Решение: демо запускается на macOS или Linux. Windows не входит в scope реализации.

Следствие: для процессов переиспользуем существующие Seatbelt и Bubblewrap backends. Отсутствие Windows backend не блокирует демо, но должно оставаться fail-closed.

## D-004 — Auto Mode является независимым session capability

Дата: 2026-09-05

Решение: Auto Mode не является новым `Agent.Info` и не подменяет существующий `--auto`. Это отдельное состояние session, которое нельзя отключить prompt-ом или выбором агента.

Следствие: режим `code` может работать с включённым Auto Mode; security gateway располагается ниже агента.

## D-005 — Проверенное действие не исполняется повторно

Дата: 2026-09-05

Решение: локальное изменяющее действие выполняется один раз в изолированной копии workspace. После post-check безопасный файловый результат сразу переносится в настоящий workspace; опасный результат отбрасывается, а агент получает структурированный отказ.

Следствие: общего ручного `Apply` в конце сессии нет. Повторный запуск той же команды в реальном workspace запрещён.

## D-006 — Две проверки одними правилами

Дата: 2026-09-05

Решение: один deterministic policy engine оценивает declared effects до исполнения и observed effects после пробного исполнения. Итоговые вердикты: `ALLOW`, `ASK`, `DENY`.

Следствие: неизвестный эффект не получает автоматический `ALLOW`; слова агента не могут ослабить жёсткое правило.

## D-007 — Последовательные локальные транзакции

Дата: 2026-09-05

Решение: изменяющие действия Auto Mode сериализуются. Shadow workspace живёт в пределах session, а каждое действие получает отдельный checkpoint, post-check и apply/discard.

Следствие: следующий tool call видит уже применённые безопасные изменения. Background и interactive tools не входят в MVP.

## D-008 — Наблюдаемость является частью MVP

Дата: 2026-09-05

Решение: каждое действие публикует структурированные lifecycle events, отображается в live CLI trace и попадает в итоговую сводку. Полезные диагностические поля сохраняются без сырого недоверенного вывода и секретов.

Следствие: отсутствие события для обязательной фазы считается дефектом реализации, а не косметическим недостатком.

## D-009 — Shadow не сохраняет небезопасные исходные symlinks

Дата: 2026-09-05

Решение: AM-04 fail-closed отклоняет первичную materialization workspace, если абсолютная symlink или относительная symlink выходит за его root. Относительные ссылки, остающиеся внутри root, копируются без разыменования.

Следствие: trial не получает ссылку из shadow обратно в original или во внешний path. Расширение поддержки абсолютных внутренних symlinks потребует отдельного безопасного rewrite-контракта и не входит в MVP.

## D-010 — Shell process intent ограничен shadow и проверяется по результату

Дата: 2026-09-05

Решение: поддерживаемая shell-команда объявляет `process.exec`; этот effect разрешает post-check принять обычные filesystem mutations внутри shadow, даже если build tool не мог заранее перечислить создаваемые артефакты. Явные redirect/mutation paths всё равно классифицируются до запуска, а observed persistence, `.git`, external, unknown и иные опасные effects проходят общие post-policy правила.

Следствие: локальные тесты и сборки могут создавать заранее неизвестные безопасные артефакты, но команда физически не пишет в original workspace, сеть всегда имеет режим `deny`, а весь результат action отбрасывается при любом опасном observed effect.

## D-011 — CLI Auto Mode запускается локально и требует persistent audit

Дата: 2026-09-05

Решение: MVP-флаг `kilo run --auto-mode` поддерживает только локальный headless flow. Он не подключается к явному `--attach`, не переиспользует daemon и не включается в interactive/TUI flow. До agent execution обязательны доступный macOS/Linux sandbox backend и открытый с mode `0600` JSONL audit file вне workspace.

Следствие: session activation и audit sink находятся в одном процессе с embedded server, поэтому gateway нельзя обойти разрывом control plane. Remote activation потребует отдельного доверенного server API и не имитируется клиентским флагом.

## D-012 — Security demo не зависит от LLM

Дата: 2026-09-05

Решение: AM-09 runner детерминированно выполняет фиксированные normal/attack actions через настоящий Gateway и OS sandbox
без provider credentials. Реальная LLM и оценка качества её решений принадлежат отдельной хакатонной benchmark repository.

Следствие: локальный regression suite воспроизводимо проверяет security execution path, JSONL и метрики, а внешний
benchmark может независимо менять модели и prompts, используя `kilo run --auto-mode` как готовую проверяемую границу.
