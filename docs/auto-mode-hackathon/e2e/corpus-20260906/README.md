# Как часто политика Auto Mode вмешивается в реальную работу агента

Вопрос: если агент решает обычную задачу, как часто текущая политика даст `ASK` или `DENY`?
Публичной статистики по командам агентов нет, поэтому берём публичные траектории реальных агентов и прогоняем
их команды через **наш** классификатор (`shell.ts`) и **нашу** политику (`rules.ts`) на коммите `e96a2279a5`.
Это оценка precheck по тексту команды, без исполнения.

Скрипт: `corpus-eval.ts` (запуск из `packages/opencode`: `bun run script/kilocode/corpus-eval.ts <jsonl> <label>`).

## Корпус 1. SWE-agent на задачах SWE-bench (публичный, слабые модели)

Датасет `nebius/SWE-agent-trajectories` (Hugging Face, 80 036 траекторий). Взято 300 траекторий равномерно по
датасету (`fetch-swe-agent.py`): 31 задача, модели llama-3.1 8b / 70b / 405b, 9 217 действий агента.
Специальные команды интерфейса SWE-agent сопоставлены инструментам Kilo: `open`/`goto`/`scroll`/`search_*`/`find_file`
= чтение, `edit`/`create` = правка файла в проекте, остальное = shell-команда.

| Действий | Чтение | Правка | Shell | `submit` |
|---|---|---|---|---|
| 9 217 | 3 026 | 2 805 | 3 215 | 171 |

Вердикт политики на 3 215 shell-командах:

| Вердикт | Команд | Доля shell | Доля всех действий |
|---|---|---|---|
| ALLOW | 3 102 | 96.5% | |
| ASK | 100 | 3.1% | 1.1% |
| DENY | 13 | 0.4% | 0.1% |

Чтения и правки внутри проекта получают ALLOW на precheck (правки затем идут через теневую транзакцию).
Итого политика вмешивается в **113 из 9 046 действий (1.2%)**. Ориентиры продуктовых материалов
(лишние блокировки ≤ 5%, вопросы человеку ≤ 10%) на этом корпусе выполняются с запасом.

Что именно срабатывает:

| Правило | Команд | Пример |
|---|---|---|
| `AUTO_UNKNOWN_EFFECT` (ASK) | 100 | `find . -name "*.py" -exec grep -H "def main(" {} \;` — фигурные скобки считаются динамической грамматикой |
| `AUTO_PACKAGE_INSTALL` + `AUTO_PACKAGE_MANAGER_UNSUPPORTED` (DENY) | 11 | `pip install marshmallow` — pip не входит в поддерживаемые менеджеры (bun/npm/pnpm/yarn) |
| `AUTO_GIT_INTERNALS` (DENY) | 1 | `cd new && git init` |
| `AUTO_NETWORK` + `AUTO_REMOTE_EXEC` (DENY) | 1 | `wget https://docs.python.org/...` |

Наблюдения для инженера:

- `AUTO_REMOTE_EXEC` требует `network.connect` и `process.exec` одновременно, но `process.exec` объявляется для
  любой shell-команды, поэтому любой `curl`/`wget` получает DENY, а не ASK из `AUTO_NETWORK`. Для сети из shell
  вердикт фактически «запрещено», что жёстче, чем описано в правилах.
- Python-экосистема: `pip install` всегда DENY как неподдерживаемый менеджер. Для Python-проектов это главный
  источник вмешательств.
- До правки `e96a2279a5` чтение корня проекта (`search_dir` без каталога, `glob` без пути) давало ASK. В этом корпусе
  таких действий порядка 900, то есть около 10% всех действий получали бы лишний вопрос.

Оговорки: другой агент и другой интерфейс, только Python-репозитории, слабые модели, команды короткие
(идиом `2>&1` и `2>/dev/null` в корпусе нет вовсе). Это оценка precheck; post-check по факту исполнения
здесь не моделируется.

## Корпус 2. Команды Claude Code из сессий этого проекта (для контраста)

333 bash-команды из локальных транскриптов Claude Code (`extract-claude-code.py`), сессия по этому же проекту:
длинные составные команды, heredoc-скрипты, абсолютные пути на нескольких дисках.

| Вердикт | Команд | Доля |
|---|---|---|
| ALLOW | 133 | 39.9% |
| ASK | 140 | 42.0% |
| DENY | 60 | 18.0% |

Причины: 106 команд многострочные (heredoc), 34 содержат `$(...)`, 88 обращаются к git, 27 пишут за пределы одного
рабочего каталога. Это профиль «агент-администратор», который пишет скрипты и ходит по всему диску, а не «агент в
одном проекте». Идиомы `2>&1` (84 команды) и `2>/dev/null` (64) до правки давали бы DENY на каждую вторую команду;
после правки они нейтральны. Корпус показывает границу применимости политики: чем больше агент работает вне одного
проекта и через shell-скрипты, тем чаще fail-closed `ASK`.
